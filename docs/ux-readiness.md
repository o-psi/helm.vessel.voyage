# Helm UX readiness

**Current verdict: not certified for first release.** This is the interaction
inventory and proposed manual acceptance gate, not a claim that every journey is
implemented, exercised, or approved. [#14](https://github.com/o-psi/voyage/issues/14)
tracks the complete interface; [#143](https://github.com/o-psi/voyage/issues/143)
is the terminal and readable-presentation slice; [#150](https://github.com/o-psi/voyage/issues/150)
tracks the chat-log reading pass. Product-owner visual acceptance
remains pending. Passing the seven [quality gates](quality.md) cannot establish UX
readiness. Historical observations are scoped in [implementation](implementation.md).

## What counts as complete

A journey starts with a user intention and ends with an understandable outcome or
an actionable recovery path. A command handler or successful API response alone
is not a usable journey. This checklist is internal to development and review.
The product should expose user intentions, names, choices and outcomes rather than
UUIDs, revisions, protocol fields, schemas or a diagnostic checklist. Engineering
details belong in explicit developer diagnostics, not the everyday interface. The user must be able to discover the action, identify its
target, understand where input goes, observe progress, and recover without copying
implementation identifiers or guessing whether an effect happened.

For each first-release journey, require all six decisions below:

| Criterion | Acceptance |
| --- | --- |
| Discoverability | A new user can find it from the relevant screen or contextual help without being coached. A slash command alone is insufficient for a primary task. |
| Target and focus | The voyage, executing host and input destination are visible. Switching, delayed responses and resize cannot silently redirect an action. |
| Outcome | Distinguish requested, admitted, working, awaiting input, completed, failed and unknown. Cancellation requested is not observed cleanup. |
| Recovery | Explain what happened, what is retained, what the user can do next, and whether retry is safe. Preserve drafts and unresolved command identities. |
| Presentation | Readable hierarchy, field labels and selection; no wire JSON dumps, replacement glyphs generated by the renderer, inaccessible overflow or hidden essential controls. Deliberately authored code examples retain their meaning. |
| Review | Exact-build interaction evidence and representative screen captures have been reviewed by the product owner. Functional verification and visual approval are separate. |

No average score overrides a failed authority, privacy, data-loss or ambiguous-effect
criterion. A polished happy path cannot compensate for an unusable recovery path.

### Planned inference selectors (#177)

Target UX for J25 and J07/J12 recovery, associated with
[#177](https://github.com/o-psi/voyage/issues/177). This is an acceptance contract,
not implementation or interaction-test evidence. See [current state](current-state.md)
for existing behavior.

- **Discover and choose:** clickable **Model**, **Thinking** and **Service**
  controls beside the composer show the selection and open a searchable modal.
  Type to filter, Up/Down to navigate, Enter to select, and Esc to cancel without
  changing settings or losing composer text.
- **One path:** `/model`, `/thinking` and `/service` open the corresponding picker.
  Typed arguments use the same validation, confirmation and submission path as
  clicks; they do not bypass safeguards.
- **Defaults and model changes:** `default` clears the corresponding explicit
  override and inherits the applicable default, rather than sending a literal
  provider value. Changing model with Thinking or Service overrides requires
  explicit confirmation: reset both overrides atomically, or explicitly keep them
  for runtime/provider compatibility validation. Show what will be cleared; cancel
  retains the old model and overrides. Never silently reset them or silently carry
  incompatible overrides to the new model.
- **Capabilities:** offer choices from live capabilities for the selected
  model/provider on the executing host. Distinguish unknown or unavailable data
  from known unsupported choices. Unknown typed values remain subject to runtime
  validation, not an assurance of support. Local configuration drafts show only
  transport-known choices, not model/account support claims. Remote drafts retain
  executing-host settings. Surface refusal without claiming a change.
- **Pending and recovery:** durably retain the pending action and preserve composer
  text across disconnect/restart. Distinguish pending from confirmed settings and
  prevent conflicting edits while the outcome is unknown. Helm automatically reconciles the
  original action without replaying it or replacing its identity. Definite refusal
  preserves text and returns to an actionable editing state.
- **Active turns:** accepted changes apply to the next turn only. Say so while a
  turn is active; its model, thinking and service do not change midway.

Manual acceptance must cover click/slash parity, search and keyboard cancellation,
default clearing, model-reset confirm/cancel, live versus unknown capabilities,
runtime refusal, automatic durable pending recovery, and active-turn timing. Preserve
a nonempty composer throughout; record actual results separately from this plan.

## State, input and layout coverage

For each journey, mark every state **exercised**, **not exercised**, or **not
applicable with reason**. The minimum state vocabulary is: unavailable/disabled,
empty, loading, ready, editing, submitting, admitted, running, waiting for human,
success, refusal, failure, timeout, cancellation requested, cleanup unresolved,
cleanup observed, disconnected, reconnected/stale and outcome unknown.

Do not require a meaningless Cartesian product. Every meaningful transition needs
coverage; authority, privacy and effectful actions require the relevant adverse
transitions on each supported route. In particular: submit then disconnect; cancel
then observe late output; switch voyage while a response is in flight; expire a
request while typing; resize between displaying and acting; change incarnation
between selecting and attaching; lose the receipt after an external effect.

Exercise these view/input families:

| Dimension | Required examples |
| --- | --- |
| Size | 80x24 baseline; 120x32 and 180x48 wide; 40x18 constrained; shrink below supported size and expand again. Essential controls must remain visible or the action must be disabled with a useful resize message. |
| Content | Empty, one item, many items; long names/paths; multiline input; long unbroken strings; tables/code; CJK and combining graphemes; terminal controls; structured payloads. |
| Input | Keyboard-only discovery and return paths, focus indicators, paste without submission, repeat keys without accidental consent, PageUp/PageDown, wheel scrolling where advertised. |
| Environment | Color and NO_COLOR; standard fonts without private-use icons; local HTTP/scoped HTTPS and SSH compatibility routes as promised; actual native platforms separately. |
| Concurrency | Multiple voyages and requests, background completion, changing inventory, disconnected host, permission changes, stale selection. |

A mocked screenshot can help design a missing state; label it **design only**.
An actual capture proves appearance for its recorded environment, not all fonts,
transports, platforms or runtime outcomes. A static image cannot establish focus,
keyboard routing, privacy or recovery.

## Evidence and review procedure

1. Select the release journeys and supported environments explicitly on #14. Assign
   an owner to each row and link its implementation/gap issue. Keep missing paths
   visible; do not mark them done because a generic JSON request can invoke them.
2. Specify expected screens, controls and transitions before fixing each journey.
   Build a review gallery from real renders; use clearly labeled designs only for
   absent states. Review language, density, focus and recovery alongside appearance.
3. Exercise an isolated real Helm -> Vessel -> voyage flow using harmless local
   programs and private temporary data. Use approved providers/budgets only when
   live provider evidence is required. Do not touch real user secrets or publish
   their console contents in captures.
4. Record the exact commit/binary hash, OS/terminal/font, dimensions, route, initial
   state, steps, expected and observed outcomes, capture paths, cleanup and issue.
   For input privacy use a dummy marker and inspect persistence; never record an
   actual password. Failures are findings, not passing evidence.
5. Have a reviewer unfamiliar with the implementation perform the task from its
   starting screen without verbal hints. Record every place they ask “where?”,
   “what happened?”, “is it still running?” or “can I safely retry?”. Resolve those
   gaps, then request the product owner's visual/interaction acceptance.
6. Repeat affected scenarios after changes. Freeze exact release evidence and
   close only verified scope. Complete the separate build/packaging gates.

Use this record for each scenario (separate rows for different outcomes):

| Field | Record |
| --- | --- |
| Journey and scenario | Jxx, named outcome/transition, linked issue |
| Build and environment | Commit, binary hash, OS, terminal/font, size, route |
| Setup and actions | Reproducible starting state and exact human steps |
| Expected / observed | Visible screen, focus/input destination and runtime outcome |
| Evidence | Capture/recording paths and narrow/wide variants; sanitized local resource observations |
| Functional result | Verified / failed / not exercised; explicit limits |
| Product review | Accepted by named reviewer and date / changes requested / pending |
| Remaining gap | Issue, owner and blocking scope |
| Cleanup | Owned processes/resources and observed cleanup or retained obligations |

The release decision reports **inventory coverage**, **functional scenario
coverage**, and **product acceptance** separately. Shipping requires 100% of the
agreed first-release journeys accounted for, all required scenarios verified, all
blocking findings resolved, and explicit product acceptance. Unreviewed and
unexercised are not synonyms for passing. Change the promised release scope only
by an explicit recorded product decision, not by hiding a failed row.

The repository currently has no automated tests/evaluations. This document adds
no replacement suite. A deterministic screen gallery, keyboard-routing checks,
protocol-to-action coverage checks and repeatable failure fixtures would be useful
future work, but need their own authorized implementation. Manual evidence and
review are the available gate now.
